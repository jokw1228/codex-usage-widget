# 배포 운영

## 권장 구조

오픈소스 desktop 앱에서 흔한 구조는 다음과 같다.

- 소스코드: GitHub repository
- 자동 빌드: GitHub Actions
- 사용자 다운로드: GitHub Releases의 asset
- 로컬 빌드 산출물: `release/` 같은 ignored folder

실행 파일을 repo에 직접 커밋하지 않는 쪽이 관리하기 좋다. 소스 변경 이력과 바이너리 배포 이력이 분리되고, 사용자는 Releases에서 버전별 파일을 받으면 된다.

## 현재 배포물

인스톨러는 만들지 않고 portable exe만 만든다.

```powershell
npm run package:win
```

결과물:

```text
release/codex-usage-widget-<version>-portable-x64.exe
```

빌드 과정에서 `assets/app-icon.png`를 `assets/app-icon.ico`로 변환하고, 이 `.ico`를 Windows 실행 파일 아이콘으로 사용한다.

`npm run package:win`은 빌드 전 `release/`를 비우고, 빌드 후에는 portable exe를 제외한 중간 산출물을 정리한다. 그래서 로컬 배포 폴더에는 최신 exe 하나만 남는 것을 목표로 한다.

## Portable 앱의 데이터 저장

현재 앱은 설정 파일을 직접 저장하지 않는다. 다만 Electron/Chromium은 기본적으로 앱 데이터, 캐시, 세션 데이터를 OS의 사용자 데이터 경로에 만들 수 있다.

Windows 기준으로 일반적인 위치는 `%APPDATA%/<앱 이름>` 계열이다. Electron 공식 문서도 `userData`를 앱 설정 파일 저장 위치로 설명하고, 기본값은 `appData` 아래 앱 이름 폴더라고 설명한다.

완전히 portable한 앱처럼 exe 옆 `data/`에 설정을 저장하게 만들 수도 있지만, Windows 데스크톱 앱에서는 사용자별 AppData를 쓰는 방식이 보통 더 안전하다. exe가 `Downloads`, `Program Files`, 동기화 폴더처럼 쓰기 권한이나 보안 정책이 다른 위치에 있을 수 있기 때문이다.

이 프로젝트는 당장은 저장할 설정이 없으므로 기본값을 유지한다. 나중에 위치/투명도 같은 사용자 설정을 저장하게 되면 `app.getPath("userData")` 아래 작은 JSON 파일로 저장하는 쪽을 우선 검토한다.
